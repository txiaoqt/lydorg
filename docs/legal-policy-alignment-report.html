Legal Policy Alignment Review

Y-TRACE Privacy Policy and Terms of Service, version 1.0 (effective June 30, 2026) · Checked against the codebase and both Supabase databases on November 5, 2026

Verdict: Most of what the policies promise is true in the system: per-version policy acceptance, role-based access with Row Level Security, audit logs with IP and user agent, no analytics or advertising tracking, no payments or e-signatures, and retention of official records on account closure. Four gaps must be closed before launch: the office name, unlisted service providers, the data location, and an undefined backup retention period.

4 must fix 6 should fix 11 confirmed aligned

Must fix before launch

1

The live policy says "LYDO"; the rest of the site says "PCYDO"

Found
The active policy in both databases (policy_versions, version 1.0) uses "LYDO" throughout and defines it as "(LYDO/PCYDO)". The copy built into the app uses "PCYDO". The public website, About page and footer all use PCYDO. Visitors see the database copy.
Decision
Use PCYDO everywhere.
Action
Replace LYDO with PCYDO in the source document and publish it as version 1.1 (see "Next steps").
2

Service providers are missing from the policy

Found
The policy names only Supabase and Vercel. The system also sends personal data to:
  • Google: "Sign in with Google" receives and returns the user's name and email.
  • Brevo: sends transactional, admin-notification and activity-announcement emails (Edge Functions send-org-transactional-email, send-admin-notification, send-activity-announcement). It receives recipients' email addresses and message content.
  • GitHub Actions: runs the database and file-storage backup (ytrace-backup.yml, triggered by admin-backup-control).
  • Cloudflare R2: stores the backup archives.
Public pages also load content from outside services, which see the visitor's IP address: OpenStreetMap map tiles and unpkg marker icons on Contacts, and Google Fonts on every page.
Decision
List all of them.
Action
Privacy Policy: name Google, Brevo, GitHub and Cloudflare in "at a Glance" and §8, add backup storage to §9, and mention map and font services in §13. Terms of Service: same list in §14.
3

The data location is not stated

Found
The new Supabase project (epfmqkgyggfpvjbjtvmv) is in ap-southeast-2 (Sydney, Australia). §9 only says data "may be handled outside the Philippines", and it ends with an internal instruction ("Before production launch, the deploying office should confirm and document…") that was never done and doesn't belong in a public policy.
Decision
Name the location.
Action
Rewrite §9 to say that the database and files are stored with Supabase in Australia (Sydney), that the site is served through Vercel's global network, and that backups are kept in Cloudflare R2 (with its region). Then delete the internal instruction sentence.
4

Backups are never deleted

Found
§10 says backups are "securely overwritten under the applicable backup cycle". No such cycle exists: nothing in scripts/backup/ removes old backups, so every backup stays in R2 indefinitely, including personal data that was later deleted.
Decision
Keep backups for 30 days.
Action
Add a lifecycle rule on the R2 bucket that deletes objects after 30 days, and change §10 to "Backups are kept for up to 30 days and then deleted."

7
