## Separate eligibility correction — not part of scenario deployment

Existing-URN verification establishes identity, **not accreditation**. A supported new-registration document approval creates term 1. A normal renewal approval creates/supersedes the next term. A/B are therefore unsuitable fixtures: A is too early; B has no ledger term. Neither was modified.

Local captured SQL reproduces a real inconsistency: a profile-only expiration can permit preview while draft creation rejects missing authoritative history. Revoked/suspended prerequisites can also differ. The previously prepared `docs/staging-validation/2026-10-10/renewal-review/proposed-eligibility-alignment.sql` aligns pointer/latest-active term lookup and prerequisites while preserving response keys/windows.

The frontend additionally labels `verifiedAt + 3 years` as authoritative and uses it for start availability. `proposed-frontend-countdown.patch` removes that estimate from authoritative countdown and requires a ledger pointer plus valid projection. **It has not been applied to application source.** Five checks execute a transpiled copy of that exact candidate; `git apply --check` passes. Existing verification-only countdown expectations must be reviewed/updated as a separate behavior correction, not silently retained as authority.

The current eligibility helper is SECURITY DEFINER with public EXECUTE and accepts another organization UUID without an owner check. The old SQL proposal preserves that ACL; it therefore **does not resolve cross-organization eligibility/expiry disclosure**. Do not approve it as a complete authorization fix. A separately reviewed private calculation core plus an owner-authorized public wrapper must account for existing custom-Admin/internal callers, which cannot simply be replaced by `auth.uid()` checks. No ACL or eligibility change was deployed here. Actual draft creation still enforces ownership and authoritative history.
